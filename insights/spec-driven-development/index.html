Spec-driven development: write the spec before the AI writes the code

AI writes code fast. So the expensive mistake isn't slow code any more. It's fast code for the wrong thing.

By Anastas Manojlovski · 20 November 2026

Contents

  2. How the workflow works
  3. Tools worth a look
  4. The limits
  5. Our three rules
  6. What are the advantages?

More and more developers are moving to spec-driven development to fix that. I talked about it at the Shipping with AI meetup at Nintex. This is the longer version.

What is spec-driven development?

GitHub puts it simply: "Instead of coding first and writing docs later, in spec-driven development, you start with a (you guessed it) spec."

The spec says what the feature must do, who it is for, and how you will know it works. A person reviews it before any code exists. Then an AI coding agent, such as Claude Code, plans the work and writes the code against the spec. GitHub calls the spec "a contract for how your code should behave".

How the workflow works

  1. Draft the spec first. Write down the problem, the functional and non-functional requirements, the inputs and outputs, the constraints, and what is out of scope. Keep it in plain files in the repository, for example requirements.md, design.md and tasks.md.
  2. Break the work into small tasks. Split each feature into small, ordered tasks that you can check one at a time. Thin vertical slices work best: each one delivers a small piece that works end to end. The agent builds one task at a time.
  3. Keep the context clean. Start a fresh context, or a separate session, for each stage: writing the spec, then building each task. Less noise in the context means less drift, fewer mistakes and lower token cost.
  4. Review early, then verify. Move most of the human review to the start: approve the spec and the task plan before the agent writes code. Then check the code and the tests against the spec.
  5. Keep improving the process. Spec-driven development is still new, and the tools change every month. Review how it works for your team regularly, and change it.

Tools worth a look

  • Spec Kit is GitHub's open-source toolkit. You run its steps as commands in your AI coding agent's chat, such as /speckit-specify, /speckit-plan, /speckit-tasks and /speckit-implement. A "constitution" holds the principles that every spec must follow.
  • OpenSpec describes itself as "fluid not rigid" and "built for brownfield not just greenfield". Each change gets a folder with a proposal, specs, a design and tasks. When the change is done, you archive it.
  • Kiro is an AI development tool from AWS. Its spec workflow goes from requirements to design to tasks, with one document for each step.

The limits

Spec-driven development is not a fix for everything. Birgitta Böckeler tested Kiro, Spec Kit and Tessl on martinfowler.com and found real problems:

  • The agent did not always follow the spec: "I frequently saw the agent ultimately not follow all the instructions."
  • The specs can be a lot to read: "I'd rather review code than all these markdown files."
  • Big up-front specs can turn into waterfall.

She also describes three levels: spec-first (write the spec for the task), spec-anchored (keep the spec and update it as the feature changes), and spec-as-source (people edit only the spec, never the code). Most teams today are at the first level.

Our three rules

Put the business outcome in the spec. "Add a claims triage screen" is a task. "Reply to every new claim within four hours, measured from the claim log" is an outcome. (This is an illustration.) The AI builds towards what the spec says, so put the outcome there.

Keep each spec small. One change, one spec. A spec that takes an hour to review will not get reviewed.

Turn acceptance criteria into tests. Write criteria that a test can check, for example "given …, when …, then …". Then a test checks the agent's work. Don't let the AI mark its own homework.

What are the advantages?

  • People agree on what to build before the code exists, when changes are cheap.
  • The agent works from a short, clear spec.
  • The spec stays as a record of why the code does what it does.
  • Reviews get easier: reviewers check the code against the spec.
