Shipping with AI: code is cheap, outcomes aren’t

Thanks for coming to Shipping with AI at Nintex. Here’s the stuff from my talk, so you don’t need a photo of every slide.

Four questions to take back to your team

  1. What business number will judge this work, and who agreed to it?

    Test it on real data, not a demo.

  2. What has to be true about your data and your controls before this goes to production?

  3. Is your customer paying for hours, or for the result?

  4. Where did AI change how the work gets done, not just how fast?

    A bot that answers handbook questions might cut tickets. If no workflow changes, park it.

If you can’t answer one of these, that’s your next piece of work. It’s probably not a prompt.

Write the spec first

AI writes code fast. So the expensive mistake isn’t slow code any more. It’s fast code for the wrong thing.

Spec-driven development changes the order. You write the spec first: what the feature must do, who it’s for, and how you’ll know it works. A person reviews the spec before any code exists. Then the agent plans the work and writes the code against the spec.

If the business outcome isn’t in the spec, the AI won’t build towards it.

Tools worth a look: Spec Kit and OpenSpec.

Sort the data out before the AI

If your data’s a mess, AI gives you confident answers from bad records.

A medallion setup is a simple way to think about it. Bronze is the raw data as it lands. Silver is cleaned up and matched. Gold is what the business actually uses. Databricks explains it well.
